# agent-code-index v1.1 优化文档

## 1. 文档目标

本文档定义 `agent-code-index` 在 v1 定版之后，进一步面向正式软件开发工程落地时的优化方向。

这份文档关注的不是“是否还能继续加功能”，而是：

1. 当前能力距离生产级工程还差哪些关键收口项
2. 哪些优化应优先进入 v1.1
3. 哪些事项可以暂时后置，不应过早增加流程复杂度
4. 如何在不破坏当前三层架构边界的前提下，把系统从“可控试运行”推进到“更稳妥的正式工程基础组件”

截至 2026-03-23，当前项目已经具备：

1. 扫描、切块、embedding、存储、检索、MCP 暴露的完整主链路
2. `voyage` 与 `openai-compatible` 两条 provider 路径的真实验证
3. SurrealDB `3.0.4` 基线下的原生 HNSW 检索
4. 五个核心 MCP tools 的真实可用能力
5. 结构化日志、日志落盘、错误序列化与基础脱敏能力

因此，v1.1 的重点不再是“把最小链路做出来”，而是把系统薄弱环节收口，提升正式工程中的可维护性、可靠性与可控性。

## 2. 当前成熟度判断

当前项目更接近：

1. 可进入正式软件开发工程中的受控落地阶段
2. 可作为内部研发团队的代码检索基础设施试运行
3. 尚未达到高可靠生产平台或大规模组织级基础设施的成熟度

当前判断依据如下：

1. 主链路已经闭环，并且不是停留在 mock 或纯设计文档阶段
2. 工程结构、测试基础、运行日志和发布产物已经具备第一版工程约束
3. 真正薄弱的部分已经从“功能缺失”转向“可靠性治理、错误模型、运行控制与长期维护”

也就是说，v1.1 的任务不是继续扩张功能面，而是优先补齐正式工程最容易出问题的能力。

## 3. v1.1 设计原则

### 3.1 优先补齐运行可靠性，而不是继续扩张功能面

当前系统已经支持真实索引与检索，因此下一步最有价值的投入，应当优先放在：

1. 外部 provider 调用可靠性
2. 索引任务稳定性
3. 故障诊断效率
4. 检索结果可控性

而不是优先增加更多 parser 语言或更多 tool 形态。

### 3.2 优先增强系统韧性，而不是优先自动化流程

当前发布频率不高，因此 GitHub Actions CI 与 Release 流程不是 v1.1 的最高优先级。

这并不意味着这类能力不重要，而是意味着在当前阶段，以下问题更值得先解决：

1. provider 抖动时系统如何退让
2. 索引失败时如何稳定保留旧数据
3. 一次异常如何快速定位到根因
4. 检索结果如何避免被噪声文件污染

因此，v1.1 明确将 GitHub Actions 相关工程化工作放入后置优化项，而不是当前主线。

### 3.3 保持三层边界稳定

v1.1 仍然遵守以下依赖方向：

1. `core` 不感知 Surreal、MCP 或具体 provider SDK
2. `infra` 负责 embedding、storage、scanner、parser 等具体实现
3. `mcp-server` 只负责配置、装配、启动校验与 tool adapter

所有优化都应尽量落在正确分层：

1. 重试、超时、限流策略主要属于 `infra` 与部分 `core` 编排边界
2. 错误码与运行链路字段属于跨包约束，但不能把协议细节反向注入 `core`
3. tool 默认值、输入回填和错误映射继续留在 `mcp-server/adapters`

## 4. v1.1 优化目标

v1.1 的目标不是把项目变成“所有场景都支持”的平台，而是让它更适合进入正式软件开发工程中的长期使用。

建议将目标收敛为以下五项：

1. 建立 provider 级可靠性治理最小闭环
2. 建立统一错误模型与可追踪诊断信息
3. 收口扫描与检索污染问题，提升结果稳定性
4. 建立索引运行安全边界与恢复策略
5. 补齐最关键的工程文档与运维约束

## 5. 优先级排序

### 5.1 P0：高优先级，建议优先进入 v1.1

#### 5.1.1 Provider 级超时、重试、退避与限流

这是当前最值得优先补齐的能力。

当前问题：

1. embedding 请求依赖外部服务
2. 当前已具备索引批次并发，但不等于 provider 自身具备可靠性治理
3. 若 provider 出现瞬时抖动、限流、超时或间歇失败，当前恢复能力仍偏弱

建议目标：

1. 为 provider 请求引入明确超时
2. 为可重试错误引入有限重试与指数退避
3. 区分可重试错误与不可重试错误
4. 建立 provider 级并发上限与节流策略

建议落点：

1. `packages/infra/src/embedding/`
2. `packages/core/src/contracts/embedding-provider.ts`
3. `packages/core/src/services/index-repository-service.ts`
4. `packages/core/src/services/index-files-service.ts`

建议验收标准：

1. 超时、429、5xx、网络错误有明确分类
2. 重试次数、退避策略和超时值可配置
3. 重试不会导致全量索引先删后空的风险扩大
4. 日志中能明确看到失败类型、重试次数与最终结果

#### 5.1.2 统一错误码与错误分类文档

当前项目已经有第一版错误分类，但还未形成对开发者真正稳定的统一错误语义。

当前问题：

1. provider、storage、MCP adapter、配置校验各自有错误，但跨模块语义尚未完全统一
2. 上层调用方难以基于稳定错误码做分支处理
3. 文档层面对错误模型的说明还不完整

建议目标：

1. 定义跨模块统一错误码前缀与命名规则
2. 明确 `validation / config / provider / storage / indexing / search / internal` 分类
3. 统一 `retryable`、`httpStatus`、`cause`、`details` 等可选字段语义
4. 在日志、tool 错误响应与内部异常模型中使用同一套语义

建议验收标准：

1. 常见错误都能映射到稳定错误码
2. 文档中能列出错误分类与调用方建议处理方式
3. MCP tool 返回的失败结构不再只是临时文本摘要

#### 5.1.3 请求链路追踪字段

当前已有结构化日志，但缺少贯穿式追踪字段。

建议目标：

1. 为索引与检索请求引入 `requestId`
2. 为一次完整索引运行引入 `indexingRunId`
3. 在 `mcp-server -> core -> infra` 的主要日志链路中向下透传
4. 对批次、worker、provider 请求建立可关联字段

建议验收标准：

1. 一次 tool 调用可以在日志中被完整串联
2. 一次失败可以定位到具体 batch、provider 调用和文件范围

#### 5.1.4 扫描与检索污染治理

这项工作对正式工程很重要，因为它直接影响检索结果质量。

需要说明的是：当前仓库已经支持通过 `DEFAULT_SCAN_GITIGNORE_PATH` 注入 `.gitignore` 规则，并可在未显式配置时自动发现根 `.gitignore`。因此，v1.1 在这一项上的重点不是“补一个全新的排除机制”，而是把现有能力收口为更稳定的默认噪声排除基线。

这里的责任边界应明确区分为两层：

1. 项目默认行为只负责排除普遍成立的工程噪声目录，例如 `node_modules`、`.git`、常见构建产物与运行日志目录
2. `results`、评测产物、团队自定义输出目录等项目特定噪声，应优先由使用方通过 `.gitignore`、`DEFAULT_SCAN_IGNORE_PATTERNS` 或更明确的部署配置自行声明

当前风险已经在 live 验证中出现：

1. 评测产物文件可能进入索引
2. 构建产物、日志、临时结果文件可能污染召回结果

建议目标：

1. 收敛默认 ignore 基线
2. 明确“项目默认排除的通用噪声”与“使用方自行配置的项目特定噪声”边界
3. 把日志、打包产物、缓存目录等通用噪声纳入更清晰的默认排除策略
4. 让质量评测结果、自定义报表、团队输出目录等项目特定噪声优先通过 `.gitignore` 或 `DEFAULT_SCAN_IGNORE_PATTERNS` 管理

建议优先关注目录：

1. `.logs/`
2. `dist/`
3. `build/`
4. `.cache/`
5. 发布产物目录与临时 `.tgz`
6. 项目自定义结果目录，例如 `test/quality/results/`，应优先通过使用方配置管理

建议验收标准：

1. 默认场景下检索结果明显减少工程噪声污染
2. 索引日志能清楚说明哪些路径被自动排除
3. 允许用户显式覆盖默认 ignore 策略，但不降低默认安全性

#### 5.1.5 索引运行安全边界与失败恢复说明

当前索引主链路已经具备“新 embedding 全部生成完成后再删旧数据”的保护，这是正确方向，但还应继续文档化和收口。

建议目标：

1. 明确 full 模式下的数据替换安全边界
2. 明确部分文件失败时的行为语义
3. 明确 provider 中断、数据库写入失败、扫描失败的恢复建议
4. 为正式工程使用者补充运行手册

建议验收标准：

1. 文档中清晰写明失败后系统保持什么状态
2. 发生异常时，使用者知道该重试什么、清理什么、保留什么

### 5.2 P1：中优先级，建议在 P0 收口后推进

#### 5.2.1 检索质量调优与可解释性增强

建议方向：

1. 继续优化 `searchText` 头部注入策略
2. 评估更稳定的 metadata filter 组合
3. 记录典型查询集上的召回质量变化
4. 增强搜索结果的 reason 与命中解释信息

这项工作重要，但优先级低于可靠性治理，因为当前系统首先要避免“失败不可控”和“定位困难”。

#### 5.2.2 `ContextBuilder` 下一阶段能力

建议方向：

1. 跨文件重排
2. query-aware summarization
3. 更精细的 token budget 分配

这属于效果增强，而不是正式工程落地的最小阻塞项。

#### 5.2.3 更多语言 parser 支持

建议方向：

1. Go
2. Java
3. Rust

这对产品扩展有价值，但对当前正式工程落地并不构成首要障碍。

### 5.3 P2：后置优化项

#### 5.3.1 GitHub Actions CI 与 Release 流程

当前判断：重要，但暂不作为 v1.1 主线优先项。

原因：

1. 当前发布频率仍然不高
2. 已有 `build:package`、`check:release` 与 `package-dist` 双轨发布流程
3. 当前更大的风险不是“没有自动化发布”，而是“运行稳定性与故障收口还需加强”

因此，当前建议是：

1. 暂时保留手工发布流程
2. 继续沿用现有发布前检查脚本
3. 待发布频率、协作人数或包数量明显提升后，再引入 GitHub Actions 与更完整的 release automation

#### 5.3.2 多包自动发版与 Changesets

当前也不建议优先引入。

原因：

1. 当前对外发布重点仍是 `@agent-code-index/mcp-server`
2. 当前收益不足以覆盖额外流程复杂度

## 6. 推荐实施顺序

建议将 v1.1 拆成三个阶段，而不是一次性并行展开。

### 阶段一：可靠性与诊断收口

优先做：

1. provider 超时、重试、退避、限流
2. 统一错误码与错误模型
3. `requestId / indexingRunId` 链路追踪

这一步的目标是让系统在失败时“可恢复、可诊断、可解释”。

### 阶段二：检索污染与运行安全收口

优先做：

1. 基于现有 `.gitignore` 注入与自动发现能力，继续收敛默认 ignore 基线
2. 质量评测结果、日志、产物目录的排除策略
3. 索引失败与恢复说明文档

这一步的目标是让系统在正式工程中“结果更稳、运行边界更清晰”。

### 阶段三：效果增强与工程补强

可做事项：

1. 检索质量调优
2. richer `ContextBuilder`
3. 更多语言 parser
4. GitHub Actions CI / Release

这一步的目标是提升长期维护效率和效果上限，但不应阻塞 v1.1 主线。

## 7. 面向正式工程使用的最低建议

如果当前项目要用于正式的软件开发工程，建议至少满足以下最低条件：

1. provider 请求具备最小超时与重试能力
2. 错误码与错误分类对外稳定
3. 日志具备请求级追踪字段
4. 现有 `.gitignore` 注入与自动发现能力已经收口为稳定默认基线，并且项目特定噪声目录可由使用方通过 `.gitignore` 或 `DEFAULT_SCAN_IGNORE_PATTERNS` 显式管理
5. 文档中明确写出索引失败后的恢复策略

只要这五项完成，当前系统就会从“可控试运行”明显推进到“更稳妥的正式工程基础组件”。

## 8. 明确不在 v1.1 主线优先处理的事项

以下事项仍然有价值，但当前不建议提升到最高优先级：

1. GitHub Actions CI 与 Release 自动化
2. Changesets 与多包自动发版
3. Web UI
4. 多数据库适配
5. 更复杂的代码图谱与影响分析
6. 面向大规模多租户的权限与隔离模型

原因很明确：

1. 当前真正制约正式工程使用的不是“流程自动化程度”
2. 而是系统在真实失败、真实抖动和真实索引污染场景下的稳定性与可控性

## 9. 结论

v1 已经证明这条路线在技术上可行，并且已经具备正式工程中的试运行价值。

v1.1 的正确方向不是继续横向扩功能，而是优先把以下几件事收口：

1. provider 可靠性治理
2. 统一错误模型
3. 请求级链路追踪
4. 索引污染控制
5. 索引失败恢复与运行手册

在当前阶段，GitHub Actions CI 与 Release 流程可以明确后置，不作为 v1.1 主线阻塞项。

这样做的收益是：

1. 可以把有限开发投入集中到最影响正式工程落地质量的地方
2. 不会因为过早引入自动化流程而分散对系统韧性问题的治理精力
3. 能以更小的复杂度，把项目推进到更稳妥的正式工程可用状态
